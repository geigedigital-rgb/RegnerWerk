# Sofort v2 — профессиональный алгоритм автоматического зонирования

**Проект:** RegnerWerk  
**Целевой модуль:** `lib/planner/v2/zoning.ts`  
**Предлагаемый этап сборки:** `v2.stage4-zone-graph`  
**Исходная версия:** `v2.stage3-2026.08`

## 1. Цель

Заменить текущую эвристику `assignHydraulicZones`, которая в основном упаковывает головы по расходу и сортирует их по углу относительно `Verteiler`, на многоэтапный алгоритм инженерного зонирования.

Новый алгоритм должен:

- создавать минимально необходимое количество клапанных зон;
- не создавать маленькую случайную «остаточную» зону;
- сохранять совместимость оборудования и режимов полива;
- учитывать форму участка и естественные геометрические границы;
- проверять расход, давление, скорость воды, потери и перепад высот;
- учитывать реальную или предварительную трассу труб;
- создавать связные и визуально понятные зоны;
- объяснять причину появления каждой зоны;
- автоматически исправлять неудачное разделение через `split`, `merge` и `rebalance`.

Главный принцип:

> Форма участка определяет, где лучше провести границу, но сама по себе не определяет, нужна ли дополнительная клапанная зона.

Если весь газон однороден и одна зона проходит по расходу и давлению, одна зона является правильным результатом даже при сложной форме. Дополнительная зона должна появляться только по конкретной инженерной причине.

## 2. Почему текущее зонирование работает нестабильно

Упрощённая текущая логика выглядит примерно так:

```ts
bucketBySprayType(heads)
sortByAngleAroundVerteiler(heads)
fillUntil(sourceFlowLpm * 0.85)
startNextZone()
```

Такой подход решает задачу упаковки по расходу, но не задачу инженерного зонирования.

Основные проблемы:

1. Головы группируются относительно распределителя, а не относительно структуры газона.
2. Первая зона заполняется почти до предела, а во вторую может попасть случайный остаток.
3. Ограничение по расходу не подтверждает наличие необходимого давления у критической головы.
4. Не учитывается, почему головы должны работать вместе: одинаковая потребность растений, интенсивность осадков, солнце, грунт, уклон, перепад высот или общий трубный коридор.
5. Граница может разрезать группу голов с сильным взаимным перекрытием.
6. Две геометрически несвязные части могут случайно попасть в одну зону, а единая часть — разделиться без понятной причины.

Пример: при суммарном расходе `36 l/min` и предварительном лимите `35 l/min` жадный алгоритм способен создать зоны `34 + 2 l/min`. Инженерно более устойчивое разбиение должно быть близко к `18 + 18 l/min`, если геометрия, трасса и гидравлика не предлагают более логичную границу.

## 3. Три разных уровня зонирования

Нельзя использовать одно понятие `zone` сразу для растительности, расписания и клапана. В модели должны существовать три разные сущности.

### 3.1 `ManagementArea` — поливочная область

Геометрическая часть ландшафта с одинаковыми условиями и потребностью в воде.

Учитываемые признаки:

- тип растительности;
- коэффициент или класс потребности в воде;
- солнце, полутень или тень;
- тип грунта и скорость инфильтрации;
- уклон;
- новый или укоренившийся газон;
- допустимая частота полива;
- ограничения по дням и времени;
- допустимая длительность одного непрерывного цикла.

Это ландшафтная гидрозона, существующая до гидравлического разделения.

### 3.2 `ScheduleGroup` — группа расписания

Несколько клапанных зон могут иметь одинаковую потребность в воде и принадлежать одной программе, но получать разную продолжительность работы из-за фактической интенсивности осадков.

Пример:

```text
SG-LAWN-SUN
├── VZ-01: 32 min
└── VZ-02: 30 min
```

Обе клапанные зоны обслуживают один тип газона и работают по одной логике расписания, но время корректируется по `precipitationMmH`.

### 3.3 `ValveZone` — физическая клапанная зона

Набор голов, одновременно работающих от одного электромагнитного клапана.

Одна `ManagementArea` может быть разделена на несколько `ValveZone` из-за расхода, давления, рельефа или трассы. Несовместимые `ManagementArea` нельзя объединять только потому, что доступного расхода формально хватает.

## 4. Место зонирования в общем потоке v2

Зонирование нельзя выполнять одним вызовом. Оно должно быть циклом проектирования и проверки.

```text
Входные полигоны и условия
→ ManagementArea
→ layout голов
→ refineHeadSet
→ HeadGraph и TrenchGraph
→ compatibility-группы
→ кандидаты ValveZone
→ предварительная трассировка
→ подбор диаметров и точная гидравлика
→ split / merge / rebalance
→ окончательная трасса
→ метрики, расписание, BOM и объяснение решений
```

### Этап A — до расстановки голов

```ts
const managementAreas = buildManagementAreas(zones, fixtures, terrain)
```

На этом этапе разделяются несовместимые требования растений и условий участка.

### Этап B — после `layout` и `refineHeadSet`

```ts
const headGraph = buildHeadAdjacencyGraph(refinedHeads, geometry)
const compatibilityGroups = buildHeadCompatibilityGroups(
  refinedHeads,
  managementAreas
)
const candidates = generateZonePartitions(
  compatibilityGroups,
  headGraph,
  sourceModel
)
```

Здесь определяется необходимое количество клапанных зон и формируются несколько логичных вариантов границ.

### Этап C — после трассировки и гидравлики

```ts
const evaluated = evaluateZoneCandidates(candidates, trenchGraph, sourceModel)
const valveZones = validateAndRepairValveZones(evaluated)
```

На этом этапе предварительное решение подтверждается или исправляется реальными потерями давления, диаметрами труб и ограничениями источника.

## 5. Обязательные причины разделения

### 5.1 Разные способы полива

Следующие методы не должны случайно попадать на один клапан:

- обычные spray;
- стандартные MP Rotator или R-VAN;
- MP800;
- strip;
- rotor;
- drip;
- bubbler или micro, если они будут добавлены.

MP800 необходимо сохранять отдельно от стандартных MP из-за несовместимой интенсивности осадков.

### 5.2 Несовместимая интенсивность осадков

Проверять необходимо не только название семейства, но и расчётную интенсивность конкретной схемы.

```ts
const precipitationBucket = classifyPrecipitation({
  nozzleFamily,
  nozzleSku,
  actualSystemPrecipitationMmH,
  layoutPattern,
  arcDeg,
  spacingM,
})
```

Полосовые сопла следует пока сохранять в отдельной группе: их фактическая интенсивность сильно зависит от геометрии и схемы размещения.

### 5.3 Разная потребность в воде

Разделение требуется, если существенно различаются:

- солнечная и теневая части;
- новый и укоренившийся газон;
- тип грунта;
- уклон и допустимая продолжительность цикла;
- плановая глубина полива;
- доступные дни или часы работы.

Рекомендуемый настраиваемый порог:

```ts
maxScheduleDemandDifferencePct: 15
```

Это продуктовый инженерный параметр, а не универсальная норма. Если данные не введены, весь газон получает единый профиль, а отсутствие данных записывается в `assumptions`.

### 5.4 Несовместимое рабочее давление

В одну клапанную зону можно объединять головы, для которых существует общий допустимый диапазон рабочего давления либо применены подходящие корпуса с регулированием давления.

### 5.5 Гидравлическая невозможность

Объединённая зона должна разделяться, если её нельзя исправить трассой или диаметрами труб и она не проходит по одному из условий:

- доступный расход источника;
- минимальное давление критической головы;
- максимальная скорость воды;
- допустимые потери в клапане и трубах;
- перепад высот;
- обязательный проектный запас давления.

### 5.6 Отдельные начерченные площади газона

Каждый отдельный полигон `Rasen` на карте — самостоятельная поливочная площадь. Даже при общей точке подключения воды (`Wasserquelle` / `Wasserverteiler`) и одинаковом режиме полива **разные полигоны газона не объединяются в одну клапанную зону**.

Пользователь рисует два несвязанных газона именно для независимого управления. В `compatibilityKey` входит `lawnComponentId` (= id полигона).

```ts
primaryReason: "DISCONNECTED_AREA"
// DE: «eigene Rasenfläche (getrennt gezeichnet)»
```

Один полигон по-прежнему может быть разбит на несколько клапанных зон из‑за расхода или давления (`SOURCE_FLOW` / `PRESSURE_MARGIN`).

## 6. Что не является самостоятельной причиной разделения

Следующие признаки сами по себе не должны создавать новую клапанную зону:

- другая сторона относительно `Verteiler`;
- переход угла через `-π / +π`;
- сложная L- или U-образная форма;
- небольшое расстояние между частями **одного** полигона;
- наличие здания внутри одного газона (форма учитывается только при уже необходимом split).

**Исключение (продуктовое правило):** разные исходные полигоны `Rasen` — это как раз обязательная причина разделения (§5.6), даже если гидравлика формально позволяет один клапан.

## 8. Граф голов вместо сортировки по углу

После `refineHeadSet` строится `HeadGraph`, где каждая голова является узлом.

Связь между двумя головами создаётся, если выполняется хотя бы одно условие:

- головы являются соседями Delaunay;
- обеспечивают взаимное `head-to-head`;
- поливают общие расчётные ячейки;
- находятся в одном ряду вдоль кромки;
- соединяются коротким допустимым трубным путём;
- принадлежат одной локальной геометрической части газона.

Сила связи должна показывать, насколько нежелательно проводить границу между головами.

```ts
interface HeadGraphEdge {
  a: string
  b: string

  sharedCoverageWeight: number
  headToHeadWeight: number
  sameRowWeight: number
  sameRegionWeight: number
  trenchDistanceM: number
  crossesNaturalSeparator: boolean

  couplingScore: number
}
```

Физически наиболее точная составляющая связи:

```text
coupling(i, j) = ∫ over lawn min(precip_i(x), precip_j(x)) dx
```

Чем больше общий вклад двух голов в распределение осадков, тем дороже разрезать эту связь границей клапанных зон.

Расстояние для зонирования следует считать не прямой линией и не углом, а кратчайшим допустимым путём по `TrenchGraph` с обходом `NO_TRENCH`.

## 9. Использование формы участка

Форма участка применяется только после того, как установлено, что разделение действительно требуется.

Предпочтительные места границы:

- узкая горловина L- или U-образного газона;
- промежуток между раздельными компонентами;
- здание, дорожка или другой естественный разделитель;
- граница между рядами голов;
- участок с минимальным количеством сильных связей графа;
- место, сокращающее длину lateral;
- разрез, после которого обе группы остаются связными.

Для поиска горловин используются `localWidth` и medial axis.

```ts
const geometricBottleneckScore =
  localWidthAtCutM / medianAdjacentRegionWidthM
```

Чем меньше отношение, тем естественнее граница. Высокий bottleneck score не создаёт дополнительную зону автоматически, а только повышает качество соответствующего кандидата, если разделение уже необходимо.

## 10. Формирование compatibility-групп

Сначала головы разделяются по жёсткой совместимости.

```ts
const compatibilityKey = [
  managementScheduleClass,
  irrigationMethod,
  precipitationBucket,
  operatingPressureClass,
  filtrationClass,
  pressureRegulationClass,
  lawnComponentId, // separate Rasen polygons → separate valve zones
].join("|")
```

Разные compatibility-группы нельзя объединять в одну клапанную зону. Исключения допустимы только как явно описанные правила совместимости, а не как неявная эвристика.

## 11. Определение необходимого количества зон

Для каждой compatibility-группы сначала рассчитывается предварительная нижняя граница.

```ts
const preliminaryTargetFlowLpm = sourceFlowLpm * zoneFillFactor
const kFlow = Math.ceil(totalDesignFlowLpm / preliminaryTargetFlowLpm)
```

`sourceFlowLpm * 0.85` остаётся только быстрым предварительным фильтром. Финальное количество зон определяется после расчёта давления и трассы.

Для кандидата рассчитывается критическое давление:

```text
Pcritical =
    Psource(Qzone)
  − fixedEquipmentLoss(Qzone)
  − valveLoss(Qzone)
  − pipeLossCriticalPath(Qzone)
  − 0.0981 × elevationRiseM

pressureMargin = Pcritical − requiredHeadPressure
```

Зона допустима, только если:

```ts
pressureMarginBar >= requiredReserveBar
maxVelocityMs <= 1.5
allHeadsInsideOperatingPressureBand === true
sourceFlowExceeded === false
routeExists === true
```

Проектный запас необходимо сделать настраиваемым. Например, для подтверждённых измерений можно использовать меньший запас, чем для расчёта с допущениями.

### Ограничение модели источника

Одна точка `Q + P_dyn` не является полноценной кривой источника. Для расходов ниже измеренного значения можно консервативно использовать измеренное давление, но нельзя экстраполировать систему выше измеренного расхода. Для интерполяции требуются минимум две подтверждённые точки `Q–P`.

## 12. Генерация кандидатов разбиения

Для каждой compatibility-группы:

1. Рассчитать минимальное предварительное `k`.
2. Проверить варианты `k`, `k + 1` и при необходимости `k + 2`.
3. Для каждого количества зон создать несколько разных начальных разбиений.

Начальные стратегии:

- разрез по узким горловинам;
- balanced graph cut;
- `k-medoids` по трубному расстоянию;
- разделение по связанным компонентам;
- разделение по расстоянию от `Verteiler`;
- разделение по рядам голов;
- разделение по углу только как один из fallback-кандидатов.

Угол относительно распределителя нельзя использовать как основную и единственную стратегию.

## 13. Balanced region growing

После выбора seed-голов зоны растут по графу.

```ts
const targetFlowLpm = totalFlowLpm / zoneCount
```

Следующая пограничная голова добавляется не в первую зону со свободным расходом, а туда, где минимален прирост общей стоимости.

```ts
const incrementalCost =
    cutConnectionsPenalty
  + fragmentationPenalty
  + routeLengthIncrease
  + pressureRiskIncrease
  + flowImbalancePenalty
  + naturalBoundaryPenalty
  + orphanZoneRiskPenalty
```

После построения выполняется локальное улучшение: пограничные головы перемещаются между соседними зонами, пока стоимость уменьшается и все жёсткие ограничения сохраняются.

## 14. Функция оценки кандидата

Сначала полностью отбрасываются кандидаты с нарушением жёстких ограничений:

- несовместимые методы полива;
- несовместимые классы осадков;
- несовместимый режим полива;
- превышение подтверждённой производительности источника;
- недостаточное давление;
- недопустимая скорость воды;
- отсутствие допустимой трассы;
- головы за пределами рабочего диапазона давления.

Для допустимых кандидатов применяется иерархическая оценка.

Приоритеты выбора:

1. Минимальное обоснованное количество клапанов.
2. Отсутствие маленькой случайной остаточной зоны.
3. Связность и понятность геометрии.
4. Достаточный запас давления.
5. Минимальная стоимость труб, фитингов и траншей.
6. Сбалансированный расход зон.
7. Минимальное пересечение сильных связей голов.
8. Минимальное суммарное окно полива.

Пример нормализованной мягкой функции стоимости:

```ts
const score =
    0.24 * valveCountCost
  + 0.18 * orphanZoneCost
  + 0.16 * fragmentationCost
  + 0.14 * hydraulicRiskCost
  + 0.10 * routeCost
  + 0.08 * flowImbalanceCost
  + 0.06 * couplingCutCost
  + 0.04 * wateringWindowCost
```

Численные веса должны быть параметрами конфигурации и калиброваться на тестовых и реальных проектах. Жёсткие ограничения нельзя заменять большими штрафами: недопустимый кандидат должен быть отвергнут полностью.

## 15. Защита от бессмысленной второй зоны

Добавляется отдельный валидатор `UNEXPLAINED_ORPHAN_ZONE`.

```ts
if (
  zone.isSmallRelativeToSibling &&
  zone.hasSameCompatibilityKey &&
  siblingHasHydraulicCapacityForMerge &&
  noHardSeparationReason(zone, sibling)
) {
  rejectCandidate("UNEXPLAINED_ORPHAN_ZONE")
}
```

Признаки подозрительной остаточной зоны:

- расход заметно ниже среднего по соседним зонам;
- одна или две головы без отдельной причины совместимости;
- высокая доля сильных связей с соседней зоной;
- отсутствие естественной геометрической границы;
- объединение проходит по расходу и давлению;
- небольшое увеличение трубы устраняет гидравлическую проблему.

Перед сохранением маленькой зоны алгоритм должен последовательно попробовать:

1. перебалансировать обе зоны;
2. перенести пограничные головы;
3. выбрать другую геометрическую границу;
4. построить альтернативную топологию труб;
5. увеличить диаметр на критическом сегменте;
6. локально пересмотреть сопла без ухудшения `DU` и `head-to-head`;
7. использовать более однородное семейство голов;
8. только после этого оставить отдельную зону.

Маленькая зона допустима, если существует жёсткая причина. Например, три MP800 среди стандартных MP должны получить объяснение `PRECIPITATION_CLASS`, а не предупреждение orphan-zone.

## 16. Обратный цикл после точной гидравлики

Недостаток давления не должен автоматически создавать новый клапан. Сначала необходимо проверить, можно ли исправить трассу или диаметр.

```ts
for (const valveZone of valveZones) {
  if (!valveZone.hydraulics.pressurePassed) {
    tryRebalanceBoundaryHeads(valveZone)
    tryAlternativePipeTopology(valveZone)
    tryLargerCriticalPipe(valveZone)

    if (!valveZone.hydraulics.pressurePassed) {
      splitZone(valveZone)
    }
  }
}

for (const [a, b] of adjacentZonePairs(valveZones)) {
  if (mergeIsFullyFeasible(a, b)) {
    evaluateMerge(a, b)
  }
}
```

После каждого существенного изменения повторяются:

1. трассировка;
2. подбор диаметра каждого сегмента;
3. итерация `P → Q/radius → losses`;
4. проверка критической головы;
5. оценка стоимости кандидата.

Чтобы ограничить время выполнения, необходимо использовать beam search или сохранять только `N` лучших кандидатов после каждого этапа.

## 17. Объяснение каждой зоны

Каждая финальная зона должна иметь понятное машинное и пользовательское объяснение.

Пример разделения по расходу:

> Зона VZ-02 обслуживает северо-западную часть газона. Она отделена от VZ-01, потому что совместный расход 52 l/min превышает подтверждённую гидравлическую производительность 34 l/min. Граница выбрана в узкой горловине около здания. Расходы распределены 25,8 и 26,2 l/min. Обе зоны принадлежат одной программе полива газона.

Пример разделения по интенсивности:

> Зона VZ-04 содержит MP800 и работает отдельно, потому что её расчётная интенсивность осадков несовместима со стандартными MP Rotator.

Пример отказа от объединения по давлению:

> VZ-01 и VZ-02 не объединены: при совместной работе расчётный запас давления критической головы составил бы 0,08 bar при требуемом минимуме 0,25 bar. Увеличение критического сегмента до PE32 не устраняет ограничение источника.

## 19. Изменения в расчёте покрытия

Метрики из `coverage.ts` необходимо считать на трёх уровнях:

- по всей `ManagementArea`;
- по `ScheduleGroup` с учётом последовательной работы связанных клапанов;
- диагностически по каждой `ValveZone`.

Иначе разделение одного газона на два последовательных клапана может ошибочно выглядеть как ухудшение покрытия, хотя геометрия полива не изменилась.

## 20. Детерминированность и устойчивость

Алгоритм должен выдавать стабильный результат при небольших изменениях входа.

Требования:

- фиксированный seed для стохастических стратегий;
- стабильная сортировка по постоянным идентификаторам;
- нормализация обхода полигонов;
- геометрические допуски для почти равных расстояний;
- штраф за полную перестройку зон при незначительном изменении координат;
- каноническая нумерация зон после выбора результата;
- независимость от порядка вершин и порядка входных объектов.

Для повторного расчёта существующего проекта полезно применять `partitionStabilityCost`, если старое разбиение всё ещё допустимо.

## 21. Ограничение вычислительной сложности

Полный перебор всех разбиений невозможен. Рекомендуемый подход:

1. Жёстко разделить головы по compatibility-группам.
2. Для каждой группы проверить не более трёх значений количества зон.
3. Создать ограниченное число seed-разбиений каждой стратегией.
4. Выполнить быстрый гидравлический envelope-check.
5. Оставить `beamWidth` лучших кандидатов.
6. Только для них выполнять реальную трассировку и точный гидравлический расчёт.
7. Локальный `split/merge/rebalance` выполнять с ограничением числа итераций.

Пример конфигурации:

```ts
interface ZoningConfig {
  zoneFillFactor: number
  maxScheduleDemandDifferencePct: number
  maxVelocityMs: number
  requiredPressureReserveBar: number

  maxAdditionalZoneCounts: number
  seedsPerStrategy: number
  beamWidth: number
  maxLocalImproveIterations: number
  maxRepairIterations: number

  orphanZoneFlowRatio: number
  orphanZoneHeadCount: number
  stabilityWeight: number
}
```

## 22. Обязательные тесты

Новая система должна проходить как минимум следующие сценарии.

### Базовая логика

- Однородный сложный газон укладывается в гидравлику → одна зона.
- Расход превышен на одну голову → две сбалансированные зоны, а не `максимум + остаток`.
- Маленькая вторая зона без жёсткой причины → кандидат отклонён.
- Маленькая зона с MP800 → зона сохранена с причиной `PRECIPITATION_CLASS`.

### Геометрия

- L-образный газон → граница в горловине.
- U-образный газон → связные зоны без чередования голов.
- Газон вокруг здания → связанные блоки, а не сортировка по углу.
- Несколько маленьких раздельных газонов (отдельные полигоны) → **отдельные клапаны** (`DISCONNECTED_AREA`), даже при общем источнике.
- Две части с дорогой или `NO_TRENCH` между ними внутри одного полигона → учитывается реальный трубный путь.

### Условия полива

- Солнце и тень → разные `ScheduleGroup`.
- Новый и укоренившийся газон → разные `ManagementArea`.
- MP800 и стандартный MP → разные клапаны.
- Strip и стандартный spray → разделение по precipitation bucket.

### Гидравлика

- Слабое давление → перебор трассы и диаметра до создания дополнительного клапана.
- Большой перепад высот → разделение или регулирование давления.
- PE32 на критическом участке делает объединение допустимым → лишний клапан удаляется.
- Одна измеренная точка Q–P → отсутствие экстраполяции выше измеренного расхода.

### Устойчивость

- Hunter ↔ Rain Bird → полный пересчёт групп и гидравлики.
- Поворот проекта на 90° → эквивалентное зонирование.
- Изменение координат на несколько сантиметров → нет случайной полной перестройки.
- Изменение порядка вершин полигона → тот же результат.
- Изменение порядка входных голов → тот же результат.

### Объяснимость

- У каждой дополнительной зоны есть `primaryReason`.
- Для каждой пары соседних зон объяснён отказ от объединения.
- В интерфейсе отображаются расход, лимит, запас давления и логика выбора границы.

## 23. Рекомендуемый порядок внедрения

### Этап 1 — правильная модель и устранение случайных зон

- добавить `ManagementArea`, `ScheduleGroup`, `ValveZone`;
- ввести compatibility-группы;
- заменить жадное заполнение на сбалансированное разбиение;
- добавить `UNEXPLAINED_ORPHAN_ZONE`;
- выдавать `ZoneDecision`.

### Этап 2 — граф и геометрия

- построить `HeadGraph`;
- использовать общие ячейки покрытия и `head-to-head` как связи;
- добавить connected region growing;
- использовать `localWidth` и bottleneck cuts;
- учитывать `TrenchGraph` вместо прямого расстояния.

### Этап 3 — route-aware гидравлика

- генерировать несколько кандидатов топологии;
- выполнять точный расчёт для лучших разбиений;
- добавить `split/merge/rebalance`;
- учитывать окно полива;
- откалибровать веса на реальных проектах.

## 24. Критерий готовности

Модуль можно считать готовым к выпуску, если выполняются все условия:

- каждая зона имеет технически проверенную причину существования;
- объединение соседних совместимых зон было явно проверено;
- нет случайной зоны из одной-двух голов без жёсткой причины;
- границы зон связны и проходят по понятным геометрическим местам;
- давление подтверждено на критическом пути;
- диаметр выбран по каждому сегменту;
- итог не зависит от порядка входных данных и поворота проекта;
- все обязательные тестовые геометрии проходят стабильно.

## 25. Итоговая архитектура

Ключевая замена:

```ts
assignHydraulicZones(...)
```

на:

```ts
const designValveZones =
  classifyManagementAreas
  + compatibilityGrouping
  + balancedGraphPartition
  + routeAwareHydraulicValidation
  + splitMergeRepair
  + decisionExplanation
```

Такой алгоритм повторяет последовательность работы профессионального проектировщика:

1. определить одинаковые потребности и режим полива;
2. исключить несовместимые головы;
3. определить минимально необходимое число клапанов;
4. найти геометрически логичные и сбалансированные границы;
5. проверить реальные трассы, диаметры и давление;
6. исправить слабые варианты через `rebalance`, `merge` или `split`;
7. объяснить каждое принятое решение.
